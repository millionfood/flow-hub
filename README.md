## 🚀 1. 핵심 트러블슈팅 (Troubleshooting)

### 💡 [인프라] AWS 512MB RAM 환경 구동 프리징 해결
- **Situation (상황):** AWS Lightsail 초저사양 512MB RAM 서버 환경에서 Spring Boot 어플리케이션을 배포하고 구동할 때, JPA 메타데이터 로딩 단계에서 어떠한 에러 로그도 없이 프로세스가 강제 다운(Hang)되는 현상 발생.
- **Task (과제):** 한정된 인프라 비용(추가 사양 업그레이드 없음) 내에서 백엔드 설정 조율만으로 서버를 안정적으로 가동시켜야 함.
- **Action (행동):** 1. 리눅스 커널의 메모리 고갈 상태를 진단하고, 디스크 공간을 활용하여 2GB 크기의 스왑 메모리(SWAP File)를 강제 할당하여 물리 램의 한계를 보완.
  2. JVM의 초기 메모리 과다 점유를 방지하기 위해 구동 스크립트에 튜닝 옵션인 `-Xms200m -Xmx200m`를 지정, 메인 메모리 풋프린트를 200MB 선으로 다이어트시킴.
- **Result (결과):** MariaDB와 Spring Boot가 동시에 상주해도 리눅스 OOM 킬러에 의해 프로세스가 죽지 않고, 한정된 자원 내에서 가용성 100%로 안정적인 백그라운드(`nohup`) 서비스를 유지하는 데 성공.

### 💡 [빌드/배포] OS 환경 불일치로 인한 QueryDSL 패키지 스캔 오류
- **Situation (상황):** 로컬 개발 환경(Windows/Mac)에서는 정상적으로 컴파일 및 구동되던 프로젝트가, 리눅스(Ubuntu) 운영체제 서버 환경으로 배포만 하면 JPA 리포지토리 및 Q클래스를 인식하지 못하는 빌드 에러 발생.
- **Task (과제):** 운영체제 간 파일 시스템 및 컴파일러 인식 차이로 발생하는 경로 문제를 해결하고 빌드 파이프라인 정형화.
- **Action (행동):** 1. 로컬 인텔리제이(IntelliJ) 자체 빌드 도구와 Gradle 빌드 엔진 간의 메타데이터 경로 충돌이 원인임을 파악.
  2. IntelliJ 빌드 도구를 **Gradle 표준 엔진으로 완전히 일치**시키고 컴파일 세팅을 동기화.
  3. 캐시 무효화(`Invalidate Caches`) 작업을 거쳐 파일 시스템의 대소문자 및 경로 인식이 정렬된 깨끗한 `bootJar`를 빌드하여 재배포 진행.
- **Result (결과):** 환경에 구애받지 않는 표준 빌드 아키텍처를 확립하고, 향후 CI/CD 파이프라인 도입 시 발생할 수 있는 환경 불일치 리스크를 사전에 완벽히 제거.

### 2. 창고 및 로케이션 매핑 자동화
- 각 창고별 구역(Zone)과 행/열/단(`LOC_ROW`, `LOC_COL`, `LOC_LEVEL`)에 맞춘 고유 로케이션 코드 생성.
- 적재 위치 매핑을 통해 물류 동선 최적화 기반 마련.

### 2-1. 조건별 비동기 API 기반의 신규 로케이션 등록 시스템
- **입력 유효성 자동화:** 관리자가 새로운 로케이션을 등록할 때, 선택한 창고(`Warehouse`)와 행/열(`Row`/`Col`) 조건에 따라 실시간으로 기등록된 로케이션 목록을 비동기 API(Fetch)로 조회.
- **화면 렌더링 및 트래픽 최적화:** 페이지 전체를 새로고침(Reload)하지 않고 변경된 조건의 데이터만 동적으로 가져와 화면에 바인딩함으로써, 불필요한 서버 자원 낭비를 줄이고 부드러운 관리자 UX 제공.
![image](https://github.com/user-attachments/assets/441e4808-7869-4df6-a5c1-d45ccd01ac71)

### 2-2. 창고 상태 변경에 따른 하위 로케이션 일괄 상태 변경 (Cascading Update)
- **연쇄적 데이터 정합성 유지:** 상위 개념인 창고(`Warehouse`)가 비활성화(`USE_YN = "N"`) 되었음에도 하위 적재 공간인 로케이션(`Locations`)들이 
  활성 상태로 남아 발생할 수 있는 '고스트 로케이션 입고 오류'를 시스템적으로 원천 차단.
- **배치성 벌크 업데이트 최적화:** 창고 비활성화 이벤트 발생 시, 해당 창고 ID를 외래키(FK)로 가진 모든 로케이션 데이터의 상태값을 
  일괄 수정(Bulk Update) 처리하여 데이터 간의 생명주기(Lifecycle) 정합성을 엄격하게 제어.
![image](https://github.com/user-attachments/assets/a37ab7b7-2989-4d11-899b-8c2bae2f0aab)

### 3. 실시간 재고 이력 추적 (`STOCK_HISTORIES`)
- 재고의 이동, 조정, 입출고 등 변동 사항이 발생할 때마다 전·후 수량과 사유(`REMARK`)를 스냅샷 형태로 기록하여 철저한 감사 추적(Audit Trail) 기능 제공.
![image](https://github.com/user-attachments/assets/bcff73b4-736c-4cb1-b616-dfd14bb9ccc3)

### 4. 연결 엔티티(Stock)를 활용한 N:M 다대다 관계 해소 및 재고 설계
- **다대다 매핑 한계 극복:** 상품(`Item`)과 창고(`Warehouse`) 간의 다대다(N:M) 관계에서 발생할 수 있는 데이터 정합성 한계를 인지하고, `@ManyToMany` 구조를 배제.
- **연결 엔티티(Stock) 도입:** 두 테이블 사이에 `Stock`이라는 연결 엔티티를 중간 테이블로 직접 설계하여 `Item(1) : Stock(N)` 및 `Warehouse(1) : Stock(N)` 구조의 1:N, N:1 관계로 해소.

### 5. 비동기 API 기반의 동적 로케이션 재고 이동 시스템
- **휴먼 에러 원천 차단:** 재고 이동 시 작업자가 상품의 특성(예: 냉동/냉장/위험물)을 무시하고 엉뚱한 구역을 선택하여 데이터가 오염되는 물류 현장의 작업 실수를 시스템적으로 방어.
- **실시간 Fetch API 연동:** 상품 등록시 창고와 상품을 선택하면 JavaScript 비동기 통신을 통해 백엔드로 이동 가능 로케이션 조회를 즉시 요청.
- **조건별 동적 UI 렌더링:** 백엔드에서 해당 창고 내 '선택 상품의 보관 조건(ZONE)에 부합하고 실제 사용 가능한(USE_YN="Y") 유효 로케이션 목록'만 JSON으로 반환받아 화면의 셀렉트 박스 옵션을 실시간으로 재구성.
- **트래픽 및 비즈니스 최적화:** 전체 로케이션을 하드코어하게 로딩하지 않아 네트워크 자원을 최적화하고, 데이터가 데이터베이스단까지 넘어가서 에러가 터지기 전에 화면단에서 잘못된 입력 자체를 원천 차단(Validate Early).

### 6. Spring Security 기반 권한 분리 및 보안 강화
- **역할 기반 접근 제어 (RBAC):** 사용자의 권한을 관리자(`ADMIN`)와 일반 유저(`USER`)로 엄격히 분리하여, 
    창고 등록 및 상품 삭제 등 핵심 관리 기능은 `ADMIN` 권한 소유자만 접근 가능하도록 인가(Authorization) 처리.
- **안전한 비밀번호 관리:** `BCryptPasswordEncoder` 단방향 암호화 해시 함수를 적용하여 사용자 비밀번호를 DB 내에 안전하게 비식별화하여 저장.
- **Thymeleaf Security 연동:** 로그인한 사용자의 권한 및 세션 상태에 따라 상단 네비게이션 바(Navbar) 및 버튼(`수정/삭제`)의 노출 여부를 동적으로 제어하여 보안 및 UX 향상.

### 7. 커스텀 예외(Custom Exception) 및 @ControllerAdvice 기반 전역 예외 처리
- **비즈니스 예외 추상화:** 표준 예외에 의존하지 않고, 서비스 고유의 예외를 처리하기 위해 최상위 예외인 `BusinessException(RuntimeException 상속)`을 정의하고, 
    이를 상속받는 `DuplicateEntityException` 등 비즈니스 상황별 커스텀 예외 클래스 구조 설계.
- **유연한 예외 핸들러:** `@ControllerAdvice`를 활용해 전역 예외를 중앙 집중식으로 제어.
- **불필요한 정적 리소스 요청 방어:** 브라우저의 특정 확장 프로그램이나 자동 스캔으로 발생하는 무의미한 정적 리소스 요청(`.well-known` 등)을 `NoResourceFoundException`으로 별도 분리 
     낚아채기하여 서버 로그 오염 및 불필요한 자원 낭비 방지.
- **클린 코드 달성:** 컨트롤러 내부에서 예외 처리를 위한 지저분한 `try-catch` 및 화면 분기 로직을 완전히 걷어내고, 
    오직 비즈니스 로직에만 집중할 수 있는 구조적 정석 구현.
  
### 8. UX 기반의 상품 삭제 제한 및 휴먼 에러 방지 시스템
- **프론트엔드 선제 차단:** 재고(`Stock`)가 물려있는 상품을 오클릭으로 지웠을 때 물류 데이터 정합성이 깨지는 리스크를 방지하기 위해, 실시간 총재고량을 프론트엔드에 전달.
- **자바스크립트 유효성 검증:** 작업자가 삭제를 시도할 때 재고 수가 1개 이상이면 폼 전송(Submit)을 API 요청 전 단계에서 차단하고, Alert 경고창을 통해 작업자의 휴먼 에러를 안전하게 방어.
- **백엔드 고도화 과제 수립:** 현재는 클라이언트단 검증을 통한 UX 보호 위주로 구현되었으며, 향후 API 직접 호출(Postman 등)을 통한 우회 공격까지 완벽히 방어하기 위해 **백엔드 서비스 레이어 검증 로직 추가 및 논리 삭제(Soft Delete)** 기능 도입을 후속 과제로 설정.




## 🌐 5. 배포 및 인프라 최적화 (Deployment & Infrastructure)

- **클라우드 인프라 구축 및 JAR 배포**
  - AWS Lightsail(Ubuntu 22.04 LTS) 인스턴스를 직접 활성화하고 가상 서버 환경을 구축.
  - FileZilla를 활용해 빌드된 `bootJar(JAR)` 파일을 전송하고, 내장 톰캣 기반의 백그라운드 구동(`nohup`) 시스템을 안정적으로 프로세싱.

- **초저사양 서버 자원 최적화 (JVM & OS 튜닝)**
  - 512MB RAM이라는 극도로 제한된 하드웨어 환경에서 Spring Boot 구동 시 메모리 고갈로 서버가 뻗는 **서버 프리징(OOM) 현상** 확인.
  - 리눅스 커널 수준에서 **2GB의 스왑 메모리(SWAP)**를 강제 할당하여 가상 메모리 공간을 확보하고, 
    JVM 구동 옵션(`-Xms200m -Xmx200m`)을 적용하여 메모리 풋프린트를 최소화함으로써 비용 증가 없이 자원 최적화 구동 성공.

- **OS 환경 격리 및 빌드 트러블슈팅**
  - 로컬(Windows/Mac) 환경과 달리 운영(Linux) 환경에서만 QueryDSL 패키지 스캔 경로가 꼬여 JPA 리포지토리를 인식하지 못하는 배포 리스크 발견.
  - IntelliJ 빌드 도구를 Gradle 표준 엔진으로 일치시키고 캐시 무효화 작업을 거쳐 정렬된 JAR를 빌드·배포함으로써 OS 불일치 문제를 완벽히 해결.

- **네트워크 및 데이터베이스 보안 제어**
  - 클라우드 방화벽 규칙 설정을 통해 외부 접속이 필요한 웹 서비스 포트(8080)만 안전하게 개방.
  - 운영 DB인 MariaDB의 원격 접속 권한을 특정 IP 및 접근 계정 위주로 제한 설계하여, 실제 상용 서비스 수준의 정석적인 네트워크 보안 환경 구축.
